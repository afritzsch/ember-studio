# 12 — User Interface

**Depends on:** 07 (ProjectStore, Commands), 08 (EngineClient for meters/telemetry) · **Owns:** `App/EmberStudio/`.

SwiftUI shell, with custom AppKit `NSView`s backed by CALayer/Metal for dense canvases (D-17). The UI mutates only through `ProjectStore.perform` and gestures (MODEL-003). It never talks to the engine directly, except for read-only meters/telemetry and plugin views.

## Layout
```
┌ Toolbar: transport · tempo/sig · position (bars|time) · CPU/xrun · record/loop/metronome ┐
├ Browser (files, plugins) │ Arrange (track headers | timeline canvas) │ Inspector (track/clip/device) ┤
└ Bottom pane (tabs): Mixer · Piano Roll · Device chain · Comp editor ┘
```

### Piano roll
| ID | Requirement | Acceptance |
|---|---|---|
| UI-020 | Note canvas (layer-backed NSView), keyboard on the left, velocity lane below. Draw/select/move/resize/delete notes, quantize (grid, strength), transpose (↑/↓, ⇧ octave). | View-model tests |
| UI-021 | Audition notes on click through the engine (`previewNote` facade call routed to the track instrument). | — |

*Piano roll details (clarified in T-043).* The bottom pane's Piano Roll tab edits one MIDI clip. It opens with a double-click on a MIDI clip in the arrange view, its context menu ("Open in Piano Roll"), or **P** (`pianoRoll.open`) with a MIDI clip selected. `PianoRollModel` (view model) / `PianoRollView` (layer-backed `NSView`, `wantsUpdateLayer`; note grid in viewport-sized tiles like UI-010, keyboard, ruler and velocity lane layers, playhead layer) under `App/EmberStudio/Shell/PianoRoll/`.
- *Edits*, all through `AddNotes`/`RemoveNotes`/`MoveNotes`/`SetNoteProps`, each gesture or action one undo entry: the draw tool (default) draws a note in the clicked grid cell (snapped down, length = the last drawn/resized length, else one snap step), dragging sets its length; the select tool drags a marquee (a double-click still draws). On notes in either tool: click selects (⇧ toggles), body drag moves the selection in time (snapped, ⌘ off) and pitch, edge drags resize end or start (the other end kept), double-click deletes. Velocity lane: drag a stem up/down for the selected notes. Snap modes are UI-012's. Quantize moves note starts toward the nearest quantize-grid line by the strength (25/50/75/100 %, lengths kept; the selection, or every note with none). ↑/↓ transpose a semitone, ⇧ an octave, as far as 0…127 allows. With the canvas focused, ⌫ deletes notes, ⌘A selects all, Q quantizes.
- *Audition (UI-021)*: pressing a key (dragging plays the keys passed) or a note (unless Audition is off) sounds it through `EngineProtocol.previewNote` on the clip's track until mouse up; a drag to a new pitch sounds the new one. The note-off always reaches the engine and track that got the note-on, also when the pane hides, the clip or track changes, or the window's document is replaced.
- *Control ids (UI-052, `ui.perform`)*: `pianoRoll.open|close`, `pianoRoll.tool.draw|select`, `pianoRoll.snap.<mode>`, `pianoRoll.quantize`, `pianoRoll.quantize.grid.<mode>` (no `off`), `pianoRoll.quantize.strength.25|50|75|100`, `pianoRoll.transpose.up|down|octaveUp|octaveDown`, `pianoRoll.velocity.up|down` (±10), `pianoRoll.selectAll|deselectAll|delete`, `pianoRoll.audition`, `pianoRoll.zoom.in|out`, `pianoRoll.note.<id>.select` (visible notes), `pianoRoll.key.<pitch>` (visible keys; a toggle that holds the note while on). `ui.state` windows carry `pianoRoll`: `{open, clip, track, trackName, clipStart, clipLength, noteCount, tool, snap, quantize{grid,strength}, audition, pixelsPerBeat, keyHeight, scroll, size, focused, visiblePitches{low,high}, visibleTicks, visibleNotes[{id, start, length, pitch, velocity, selected, rect, velocityY}], selection, marquee, gesture, sounding, auditionTrack, trackMeter{peak,rms}|null, playhead{tick,x}}`.

### Mixer & devices
| ID | Requirement | Acceptance |
|---|---|---|
| UI-030 | Mixer (SwiftUI): channel strip per track/bus/master — fader (dB taper), pan, mute/solo/arm/monitor, sends, inserts list, output selector, meter. | — |
| UI-031 | Meters read `EngineClient.meter(id)` at display rate (CADisplayLink on NSView) with peak hold and clip indicator; drawn in a lightweight custom view, not SwiftUI re-render. | No SwiftUI invalidation per frame (Instruments) |
| UI-032 | Device chain view: built-in device generic UI generated from `ParamInfo` (knobs/sliders); plugin "Open Editor" button (PLUG-017); bypass; drag reorder; sidechain source picker. | — |
| UI-033 | Routing pickers reject cycles with the model's error message (MODEL-030). | — |

*Mixer details (clarified in T-076).* `MixerModel` (view model, one per window, `App/EmberStudio/Shell/Mixer/`) / `MixerPane` (`Views/MixerView.swift`), the bottom pane's Mixer tab: one strip per track, then per bus, then the master, which stays fixed at the right while the others scroll in a lazy stack. Strips are derived from the project on demand, so edits from anywhere (arrange view, undo/redo, the control socket) show with no sync of their own.
- *Strip* (UI-030): name, inserts, sends, output, pan, fader with meter and dB readout, then the switches. A track strip uses its header's controls (DW-202): the same `track.<id>.mute|solo|arm|monitor.*|input.*|select` descriptors, one per id, drawn in both places. Audio and MIDI tracks both have arm and monitoring, as their headers do; a MIDI track has no input menu. A bus has mute and solo but no arm. The master has mute only, no solo (MODEL), no output, no sends. A strip re-renders only when its own values change (`MixerStripModel ==` compares what it shows).
- *Fader and pan*: `MixerSliderView` (AppKit), since a raw `Slider` can't be driven by `ui.perform` (UI-052). Fader taper (`FaderTaper`): piecewise linear in dB through −60 dB at 0.05, −30 at 0.25, −12 at 0.5, 0 at 0.75 and +12 at 1; position 0 is silence. A drag is one undo step (`beginGesture`, `SetParam` or `SetSendLevel` per movement, `endGesture`; a press with no movement is none). It is relative to the grab. A double-click resets to 0 dB or centre. The nudges are one undo step each: faders ±1 dB (down from −60 dB is silence, up from silence is −60 dB), pan ±0.05.
- *Sends*: each shows its target, level (same taper) and a Pre toggle (on: pre-fader, off: post-fader), with remove, and "+ Send" lists every bus. Levels use `SetSendLevel`, the toggle `SetSendTap`.
- *Inserts*: read-only names with bypass state (⊘) until the insert-chain commands exist (DW-149). Up to three show, then "+N more". `ui.state` lists them all.
- *Routing pickers* (UI-033): output and send-target menus offer every bus, also ones that would close a cycle, or the strip itself. The model refuses those (MODEL-030): an error toast carries its message plus the channels' names, the project doesn't change, and the menu keeps showing the real output because it shows the project.
- *Meters* (UI-031): `MeterBank` (not `@Observable`: it changes every frame) reads `EngineProtocol.meter` once per display frame for each meter on screen and hands `ChannelMeterView`s (layer-backed) their ballistics: peak bar, instant attack, 24 dB/s release; RMS bar inside it; peak hold 1.5 s; a clip indicator latched above full scale until the meter is clicked or `clip.reset` runs. The scale is −60…+6 dB. One display link per mixer (`MeterClockView`, zero-size, in the tab): it stops when the tab is hidden or the window closes, pauses while the window is occluded, and its target holds the view weakly, so it never keeps a window alive.
- *Control ids (UI-052)*, listed while the tab is open, with `<prefix>` = `mixer.track.<id>`, `mixer.bus.<id>` or `mixer.master`: `<prefix>.fader.up|down|reset`, `<prefix>.pan.left|right|center`, `<prefix>.clip.reset`; on buses and the master also `<prefix>.mute` (and `.solo`, buses); on tracks and buses `<prefix>.output.master`, `<prefix>.output.bus.<id>` (toggles, the current output on), `<prefix>.send.add.<bus>`, and per send `<prefix>.send.<id>.level.up|down|reset`, `.tap.pre` (toggle, on: pre-fader), `.remove`. Accessibility identifiers that name views rather than controls: `<prefix>.fader`, `.pan`, `.send.<id>.level` (the sliders), `.meter`, `.gain`, `.inserts`, `.output.menu`, `.send.add.menu`, `.input.menu`, `.monitor.menu`. `ui.state` windows carry `mixer`: `{open, gesture, strips[{id, kind (audio|midi|bus|master), name, controlPrefix, selected, gain, gainDB, gainLabel, faderPosition, pan, panLabel, mute, solo, armed?, inputPair?, monitoring?, output{kind, id?, name}|null, outputChoices[{id, name, current}], sends[{id, target, targetName, level, levelDB, levelPosition, tap, controls}], sendTargets[{id, name}], inserts[{id, name, bypass}], meter{peak, rms, peakDB, rmsDB, holdDB, clipped}|null, controls}]}` (`gainDB`, `levelDB` null for silence; `peak`/`rms` are the engine's now, the others from the last display frame, so they don't advance while the tab is hidden; `controls` includes the header's `track.<id>.…` ids).

### Preferences & misc
| ID | Requirement |
|---|---|

| UI-042 | Export dialog: range (loop/whole/selection), format, bit depth, dither, normalize off by default. |

*Audio preferences details (clarified in T-055).* `AudioPreferencesModel` (`App/EmberStudio/Shell/Model/`), one per project window: each project has its own engine, so its settings belong to the window. The panel (`AudioPreferencesPanel`) is a strip under the toolbar, in the layout (an overlay would sit under the AppKit canvases), so `ui.snapshot` captures it. It opens from the toolbar's Audio toggle, ⌘, or the app menu's *Settings…*.
- *Device, buffer, input* (UI-040): output device (system default or a listed one), input device (system default or one with inputs; IO-004), buffer size 32…2048, and input channels (the device's first N: powers of two up to the device's count, plus that count). Each change calls `EngineProtocol.setDevice` with the window's config, one field edited, and rate 0. Rate 0 keeps the session rate if the device can run it. Otherwise the engine takes the device's rate and the project follows (DW-079, DW-130). A refusal posts an error toast and is kept in `error`. The engine doesn't report the config it runs, so the model keeps the last config it applied, starting from `EngineProtocol.mode`. A chosen device that is lost becomes "system default", as in the engine (IO-021). An offline engine has no device: those controls are disabled.
- *Sample rate* (DW-183): it is the project's. 44.1/48/88.2/96 kHz go through `SetSessionSampleRate` (MODEL-005, history-exempt). A rate the device can't run is refused before the document changes, with a "Set Sample Rate failed" toast.
- *Latency* (IO-005): output latency from telemetry, `outputLatency` = device (`deviceOutputLatency`: latency + safety offset + buffer) + graph (PDC), shown in ms and samples. Input latency isn't in telemetry yet.
- *Re-conversion progress* (DW-183, IO-033): from `assetsReloaded` events, `started` / `progress` (done of total) until `finished`; a new `started` supersedes a pass. It shows as a progress bar in the toolbar and in the panel. When it finishes, an info toast says "Audio converted to … kHz" (if there were assets), or a warning says how many files didn't convert.
- *Toasts* (UI-004): device toasts carry an "Audio Settings…" action that opens the panel. Warnings and infos with it still expire; errors stay. Toasts name devices from every list the window has seen, so a lost device keeps its name.
- *Control ids (UI-052)*: `prefs.audio` (toggle, always listed; ⌘,). While the panel is open: `prefs.audio.close`, `prefs.audio.refresh`, `prefs.audio.output.default|<deviceID>`, `prefs.audio.input.default|<deviceID>`, `prefs.audio.sampleRate.44100|48000|88200|96000`, `prefs.audio.buffer.32|64|128|256|512|1024|2048`, `prefs.audio.inputChannels.<n>`; all toggles except close and refresh, and the one in force is on. `ui.state` windows carry `audioPreferences`: `{open, driver (fake|coreAudio|null), devices[{id, name, inputChannels, outputChannels, nominalSampleRate, isDefaultOutput}], outputDevice, inputDevice (0: system default; null offline), runningDeviceID, deviceRunning, sampleRate (the project's), engineSampleRate, bufferFrames, inputChannels, inputChannelChoices, latency{deviceSamples, graphSamples, totalSamples, totalMs}, reload{phase, previousSampleRate, sampleRate, done, total, failed}|null, assetsReloadPending, error}`.

*Track header recording controls and recording toasts (clarified in T-055, after T-052).* A header has two lines: name, kind, mute and solo, then arm, input pair (audio tracks) and monitoring.
- *Arm* (REC-001): `track.<id>.arm` toggles `ArmTrack`; engine sync turns it into `armInput`. *Monitoring* (REC-020): `track.<id>.monitor.off|auto|on` perform `SetMonitoring`; the behaviour is T-054's. *Input* (DW-200): `track.<id>.input.<pair>` sets `ArmTrack`'s `inputPair` and keeps the arm state. It offers the pairs the running device's inputs have, as many channels as the audio settings capture: (min(device inputs, input channels) + 1) / 2 pairs. The track's own pair is always offered, so a pair set elsewhere shows and can be changed back. With no device (offline engine) only the track's own pair is offered; MIDI tracks have no input menu. All three commands are history-exempt (no undo entry). The menus are `Menu`s of toggles (`track.<id>.input.menu`, `track.<id>.monitor.menu` name the menus, not controls). `ui.state` tracks carry `armed`, `inputPair` and `monitoring`.
- *Record* (UI-002 R, `transport.record`): goes through `EngineSync.setRecording` (DW-198), which sets the recordings folder before recording starts (REC-002).
- *Toasts* (UI-004, REC-004): the store imports a take before the window sees its `recordingFinalized` event, so a toast can tell whether the take is in the project (an asset with the take's path).
  - Takes added: one info toast per event batch, "Take recorded" or "N takes recorded" with each track's name and length.
  - Dropped frames: a warning "Recording dropped audio" with the frames and ms lost (the gaps are silent; the take is still added).
  - No file: an error "Recording not saved", which stays until dismissed.
  - Empty take: an info "Nothing recorded".
  - A take that wasn't added (e.g. its track is gone): a warning "Take not added" naming the file, which is kept.
  - An event without a take (older engines) toasts only an error, as before.
