# 12 — User Interface

**Depends on:** 07 (ProjectStore, Commands), 08 (EngineClient for meters/telemetry) · **Owns:** `App/EmberStudio/`.

SwiftUI shell, with custom AppKit `NSView`s backed by CALayer/Metal for dense canvases (D-17). The UI mutates only through `ProjectStore.perform` and gestures (MODEL-003). It never talks to the engine directly, except for read-only meters/telemetry and plugin views.

## Layout
```
┌ Toolbar: transport · tempo/sig · position (bars|time) · CPU/xrun · record/loop/metronome ┐
├ Browser (collections, devices, files; UI-060) │ Arrange (track headers | timeline canvas) │ Inspector (track/clip/device) ┤
└ Bottom pane (tabs): Mixer · Piano Roll · Device chain ┘   (no comp editor tab: comping is in the arrange view, DW-272)
```

*Track list & clip creation (UI-017, UI-018; user request 2026-11-19, docs/requests/2026-11-19.md; T-122).*
- *Track list menu* (UI-017): the header column (`TrackHeaderColumn`) takes a secondary click anywhere in it: on a track header, and in the empty space under the last header. The empty timeline area under the last track gets the same menu.
  - On a track header: **New Audio Track**, **New MIDI Track** (`AddTrack {index: that track's index + 1}`), a separator, **Rename…** (the header's name field goes into editing), **Delete** (`RemoveTrack`). On empty space: the two New items, appending (`index` nil).
  - Names and colours are the ones ⌘T/⇧⌘T give (`ProjectWindowModel.addTrack`). The new track is selected. Each item is one undo entry.
  - The secondary click also selects the clicked track, as a primary click does. The menu is an `NSMenu` (from the AppKit header/canvas views, like the canvas menu at `TimelineCanvasView.menu(for:)`), so a two-finger tap works with the system's secondary-click setting.
  - *Control ids* (UI-052): `track.<id>.menu.addAudio|addMidi|rename|delete` and `tracks.menu.addAudio|addMidi`.
- *Insert MIDI clip* (UI-018): a double-click on a MIDI track's lane where no clip is (not a take row, automation lane or the empty area under the tracks) creates a clip with `AddClip` (a MIDI track's `AddClip` gives an empty MIDI clip).
  - *Start*: the click's tick snapped **down** to the grid (UI-012; snap off or ⌘ held: the exact tick).
  - *Length*: one bar of the time signature in force at the start. If that would overlap the next clip on the track, the clip ends where that clip starts. If less than one grid step (one beat with snap off) would fit, nothing is created.
  - The clip is selected and opened in the piano roll (as a double-click on a MIDI clip does). One undo entry.
  - The canvas context menu (`TimelineCanvasView.menu(for:)`) on an empty spot of a MIDI lane adds **Insert MIDI Clip**, with the same rules at the clicked position.
  - A double-click on empty space on an audio track still does nothing.
  - *ui.perform*: `track.<id>.insertMidiClip` inserts at the playhead with the same rules. A `tick` parameter is accepted (13 delta pre-accepted for T-122).

*UI-010 perf smoke (DW-223, clarified in T-090).* `ArrangePerfTests.thousandClips` measures the model's per-frame work over 1,000 clips (interval query, waveform mesh). The strict bounds, under 16 ms per frame and an index build under 50 ms, are asserted only when `DAW_PERF_TESTS=1` (the perf job). They hold on an idle machine but not under load: 50–100 ms per frame was seen with parallel workers or other apps running. The default run keeps the test with loose bounds (250 ms per frame, 500 ms to build). Those still catch a regression of an order of magnitude, such as an index rebuilt every frame or a query that scans every clip. The 60 fps acceptance itself stays an Instruments run (DW-166).

*Piano roll details (clarified in T-043).* The bottom pane's Piano Roll tab edits one MIDI clip. It opens with a double-click on a MIDI clip in the arrange view, its context menu ("Open in Piano Roll"), or **P** (`pianoRoll.open`) with a MIDI clip selected. `PianoRollModel` (view model) / `PianoRollView` (layer-backed `NSView`, `wantsUpdateLayer`; note grid in viewport-sized tiles like UI-010, keyboard, ruler and velocity lane layers, playhead layer) under `App/EmberStudio/Shell/PianoRoll/`.
- *Edits*, all through `AddNotes`/`RemoveNotes`/`MoveNotes`/`SetNoteProps`, each gesture or action one undo entry: the draw tool (default) draws a note in the clicked grid cell (snapped down, length = the last drawn/resized length, else one snap step), dragging sets its length; the select tool drags a marquee (a double-click still draws). On notes in either tool: click selects (⇧ toggles), body drag moves the selection in time (snapped, ⌘ off) and pitch, edge drags resize end or start (the other end kept), double-click deletes. Velocity lane: drag a stem up/down for the selected notes. Snap modes are UI-012's. Quantize moves note starts toward the nearest quantize-grid line by the strength (25/50/75/100 %, lengths kept; the selection, or every note with none). ↑/↓ transpose a semitone, ⇧ an octave, as far as 0…127 allows. With the canvas focused, ⌫ deletes notes, ⌘A selects all, Q quantizes.
- *Audition (UI-021)*: pressing a key (dragging plays the keys passed) or a note (unless Audition is off) sounds it through `EngineProtocol.previewNote` on the clip's track until mouse up; a drag to a new pitch sounds the new one. The note-off always reaches the engine and track that got the note-on, also when the pane hides, the clip or track changes, or the window's document is replaced.
- *Control ids (UI-052, `ui.perform`)*: `pianoRoll.open|close`, `pianoRoll.tool.draw|select`, `pianoRoll.snap.<mode>`, `pianoRoll.quantize`, `pianoRoll.quantize.grid.<mode>` (no `off`), `pianoRoll.quantize.strength.25|50|75|100`, `pianoRoll.transpose.up|down|octaveUp|octaveDown`, `pianoRoll.velocity.up|down` (±10), `pianoRoll.selectAll|deselectAll|delete`, `pianoRoll.audition`, `pianoRoll.zoom.in|out`, `pianoRoll.note.<id>.select` (visible notes), `pianoRoll.key.<pitch>` (visible keys; a toggle that holds the note while on). `ui.state` windows carry `pianoRoll`: `{open, clip, track, trackName, clipStart, clipLength, noteCount, tool, snap, quantize{grid,strength}, audition, pixelsPerBeat, keyHeight, scroll, size, focused, visiblePitches{low,high}, visibleTicks, visibleNotes[{id, start, length, pitch, velocity, selected, rect, velocityY}], selection, marquee, gesture, sounding, auditionTrack, trackMeter{peak,rms}|null, playhead{tick,x}}`.

*Mixer details (clarified in T-076).* `MixerModel` (view model, one per window, `App/EmberStudio/Shell/Mixer/`) / `MixerPane` (`Views/MixerView.swift`), the bottom pane's Mixer tab: one strip per track, then per bus, then the master, which stays fixed at the right while the others scroll in a lazy stack. Strips are derived from the project on demand, so edits from anywhere (arrange view, undo/redo, the control socket) show with no sync of their own.
- *Strip* (UI-030): name, inserts, sends, output, pan, fader with meter and dB readout, then the switches. A track strip uses its header's controls (DW-202): the same `track.<id>.mute|solo|arm|monitor.*|input.*|select` descriptors, one per id, drawn in both places. Audio and MIDI tracks both have arm and monitoring, as their headers do; a MIDI track has no input menu. A bus has mute and solo but no arm. The master has mute only, no solo (MODEL), no output, no sends. A strip re-renders only when its own values change (`MixerStripModel ==` compares what it shows).
- *Fader and pan*: `MixerSliderView` (AppKit), since a raw `Slider` can't be driven by `ui.perform` (UI-052). Fader taper (`FaderTaper`): piecewise linear in dB through −60 dB at 0.05, −30 at 0.25, −12 at 0.5, 0 at 0.75 and +12 at 1; position 0 is silence. A drag is one undo step (`beginGesture`, `SetParam` or `SetSendLevel` per movement, `endGesture`; a press with no movement is none). It is relative to the grab. A double-click resets to 0 dB or centre. The nudges are one undo step each: faders ±1 dB (down from −60 dB is silence, up from silence is −60 dB), pan ±0.05.
- *Sends*: each shows its target, level (same taper) and a Pre toggle (on: pre-fader, off: post-fader), with remove, and "+ Send" lists every bus. Levels use `SetSendLevel`, the toggle `SetSendTap`.
- *Inserts* (editable since T-065, DW-250): each row has a bypass toggle (⏻), the name (a click shows the device in the Device Chain tab), an "Edit" toggle for plugins, and a context menu to move it up/down or remove it; dragging a row onto another reorders (`MoveDevice`). "+" is the device picker (built-ins, then scanned AU/VST3 effects). Up to three show, then "+N more". `ui.state` lists them all. See *Device chain details (T-065)*.
- *Routing pickers* (UI-033): output and send-target menus offer every bus, also ones that would close a cycle, or the strip itself. The model refuses those (MODEL-030): an error toast carries its message plus the channels' names, the project doesn't change, and the menu keeps showing the real output because it shows the project.
- *Meters* (UI-031): `MeterBank` (not `@Observable`: it changes every frame) reads `EngineProtocol.meter` once per display frame for each meter on screen and hands `ChannelMeterView`s (layer-backed) their ballistics: peak bar, instant attack, 24 dB/s release; RMS bar inside it; peak hold 1.5 s; a clip indicator latched above full scale until the meter is clicked or `clip.reset` runs. The scale is −60…+6 dB. One display link per mixer (`MeterClockView`, zero-size, in the tab): it stops when the tab is hidden or the window closes, pauses while the window is occluded, and its target holds the view weakly, so it never keeps a window alive.
- *Control ids (UI-052)*, listed while the tab is open, with `<prefix>` = `mixer.track.<id>`, `mixer.bus.<id>` or `mixer.master`: `<prefix>.fader.up|down|reset`, `<prefix>.pan.left|right|center`, `<prefix>.clip.reset`; on buses and the master also `<prefix>.mute` (and `.solo`, buses); on tracks and buses `<prefix>.output.master`, `<prefix>.output.bus.<id>` (toggles, the current output on), `<prefix>.send.add.<bus>`, and per send `<prefix>.send.<id>.level.up|down|reset`, `.tap.pre` (toggle, on: pre-fader), `.remove`. Accessibility identifiers that name views rather than controls: `<prefix>.fader`, `.pan`, `.send.<id>.level` (the sliders), `.meter`, `.gain`, `.inserts`, `.output.menu`, `.send.add.menu`, `.input.menu`, `.monitor.menu`. `ui.state` windows carry `mixer`: `{open, gesture, strips[{id, kind (audio|midi|bus|master), name, controlPrefix, selected, gain, gainDB, gainLabel, faderPosition, pan, panLabel, mute, solo, armed?, inputPair?, monitoring?, output{kind, id?, name}|null, outputChoices[{id, name, current}], sends[{id, target, targetName, level, levelDB, levelPosition, tap, controls}], sendTargets[{id, name}], inserts[{id, name, bypass, safeModeBypassed, format, plugin, editorOpen}], meter{peak, rms, peakDB, rmsDB, holdDB, clipped}|null, controls}]}` (`gainDB`, `levelDB` null for silence; `peak`/`rms` are the engine's now, the others from the last display frame, so they don't advance while the tab is hidden; `controls` includes the header's `track.<id>.…` ids).

*Plugin editor details (Contract delta (T-063), accepted (autobuild, see docs/autobuild/DECISIONS.md "T-063 editors"); PLUG-017, UI-032's "Open Editor").*
- **Model and panels.** `PluginEditorModel` (one per window, `App/EmberStudio/Shell/PluginEditor/`) keeps the window's open editors. `PluginEditorPanels` shows each one in a floating utility `NSPanel` titled "<plugin> — <project>":
  - the panel's content view is the engine's container (08 `createPluginView`), so the panel follows the plugin's size;
  - the panel is resizable only when the editor is;
  - its close button closes the editor.
- **What closes an editor:**
  - its slot leaves the project (RemoveDevice, RemoveInstrument, an undo; checked at the window's poll);
  - its plugin crashes (`pluginCrashed`);
  - safe mode is on (PLUG-021; editors can't be opened then);
  - the document is replaced, or the window closes.
  An editor still in a plugin gesture ends that gesture as it closes (DW-204).
- **Engine handover** (DW-156): editors close with the old engine and reopen on the new one. An editor whose plugin instance was replaced reopens on the new one.
- **Failures:** a plugin the engine can't make an editor for (not loaded, no editor) gets an error toast, "No editor for <plugin>".
- **Control ids (UI-052)**, with the mixer's `<prefix>`, listed while the Mixer tab is open:
  - `<prefix>.insert.<slot>.editor` for each AU/VST3 insert;
  - `mixer.track.<id>.instrument.editor` for a MIDI track's plugin instrument;
  - all toggles, on while the editor is open, labelled "<plugin> Editor", and disabled without an engine or in safe mode.
  - The strip shows them as small "Edit" buttons next to the insert's name, and the instrument as a "♪ <name>" row.
- **`ui.state`:** windows carry `pluginEditors: [{slot, title, kind (au|auGeneric|vst3), width, height, ready, resizable, control}]`.
- **`ui.snapshot`** (13, additive) takes `pluginEditor?: slot` and then captures that editor's panel through `cacheDisplay` (the result adds `pluginEditor`). An unopened editor is `invalidArgument`.

*Device chain details (Contract delta (T-065), accepted (autobuild, see docs/autobuild/DECISIONS.md "T-065 scope"); UI-032, DW-196, DW-226, DW-250, DW-253, DW-254, DW-264).* `DeviceChainModel` (one per window, `Shell/DeviceChain/`) / `DeviceChainPane`, the bottom pane's Device Chain tab.
- **Channel**: the picked channel (`deviceChain.channel.<id>`: tracks, buses, the master) while it exists, else the first selected track, else the first track, else the master. A mixer insert's name (`<prefix>.insert.<slot>.show`) opens the tab on its channel.
- **Cards**, left to right: a MIDI track's instrument (♪), then the inserts in order. Each has bypass (`SetDeviceBypass`), remove (`RemoveDevice`, `RemoveInstrument`), move left/right (`MoveDevice`; also by dragging a card onto another), and for AU/VST3 an "Edit" toggle (the T-063 editor) and a ⚙ toggle for the generic controls. "+ Device" is the device picker: built-ins (EQ, Compressor, Delay, Reverb, Gain), then the plugin manager's AU and VST3 effects (instruments and blocked plugins aren't offered).
- **Generic controls**: built-ins always show theirs, from ParamInfo (06; the engine's catalog, else `ParamCatalog.builtin`). A plugin shows its `pluginInfoJSON` params on request, and on its own when the engine had no editor for it (DW-264; the error toast still shows). A param with `steps` 1 and no labels is a toggle; any other stepped or labelled param (the delay's note, the compressor's detector) is a menu of its values (DW-196); the rest are sliders (`MixerSliderView`) along the param's mapping (AUTO-008: log for Hz and ms). A value reads as its label, else number and unit. An automated param is marked "A" and shows the lane's value at the playhead.
- **Edits** (MODEL-003): a slider drag is one undo entry ("Set Parameter"), a double-click resets (a built-in's default; a plugin's param becomes not set). Drags and menu/toggle clicks go through the automation recorder like the mixer's faders (DW-254): playing on a touch/latch/write lane they record, stopped on an automated param they edit the point under the playhead. The `.up`/`.down` nudges (a twentieth of the mapped range) and `.reset` stay plain `SetParam`.
- **Sidechain** (MIX-008): the compressor, and plugins unless the engine says they have none, get a menu of every other track and bus plus None (`SetSidechain`); a source that would close a cycle is refused by the model (MODEL-030) with an error toast.
- **Safe mode** (PLUG-021, DW-226; with T-083 the engine builds these slots without their plugin, `pluginInfoJSON` `"disabled": true`): AU/VST3 cards and mixer inserts show "Disabled by safe mode": the bypass toggle is on and disabled, the editor disabled, and a card's generic controls say the plugin isn't loaded and its settings are kept. The document's own bypass is kept and reported separately; the window's banner (T-083) ends safe mode. Plugin info read before a safe-mode toggle isn't reused after it.
- **Plugin info** is read from the engine when a card needs it and re-read every 0.5 s while the tab shows (a plugin's own values move under its editor, a load finishes); a plugin not loaded yet is asked again each time.
- **"+ Lane"** (DW-253): the automation menu also lists hosted plugins' params by their `pluginInfoJSON` names (none while a plugin isn't loaded). VST3 values are normalized (DW-213).
- *Control ids (UI-052)*, listed while the tab shows: `deviceChain.channel.<id>` (toggles), `deviceChain.add.<key>` (`builtin.<node>` or `plugin.<n>`, the n-th effect the picker lists), and per device `deviceChain.device.<slot>.bypass` (toggle), `.remove`, `.moveUp`, `.moveDown` (inserts), `.editor`, `.generic` (toggles, plugins), `.sidechain.none|<channel>` (toggles), and per shown param `.param.<index>.up|down|reset` (sliders), `.param.<index>` (toggle) or `.param.<index>.value.<k>` (menu items, the current one on). The mixer's strips add `<prefix>.insert.add.<key>` and per insert `<prefix>.insert.<slot>.bypass` (toggle), `.remove`, `.up`, `.down`, `.show`. Accessibility identifiers that name views: `deviceChain.pane`, `deviceChain.channel.menu`, `deviceChain.add.menu`, `deviceChain.device.<slot>` (the card), `.safeMode`, `.sidechain.menu`, `.param.<index>` (a slider), `.param.<index>.menu`, `.param.<index>.value` (the readout), `<prefix>.insert.add.menu`.
- `ui.state` windows carry `deviceChain`: `{open, channel, channelName, channels[{id, name}], gesture{slot, index}|null, safeMode, choices[{key, name, group}], devices[{id, name, format (builtin|au|vst3), instrument, position, bypass, safeModeBypassed, plugin, loaded, loadError, disabled, editorOpen, noEditor, showsParams, acceptsSidechain, sidechain{source, name}|null, params[{index, id, name, unit, min, max, curve, steps, labels, style (slider|toggle|menu), value, display, position, set, automated, automatable}], controls}]}`.

*Plugin manager details (Contract delta (T-065), accepted (autobuild); UI-041, DW-015).* `PluginManagerModel` (`Shell/PluginManager/`, one per app, `PluginManagerModel.shared`) over the `PluginCatalog` library product (01): it reads the scan cache lazily (PLUG-004's `plugins.json`) and scans off the main actor with the `PluginScanner` helper the app embeds in `Contents/MacOS` (PLUG-001). Each window shows it in a strip under the toolbar (`PluginManagerPanel`, in the layout like the audio settings), opened by the toolbar's "Plugins" toggle.
- **Scan** (`refresh`): new and changed plugins only, vanished ones dropped. **Rescan All**: forgets the cache and scans everything. **Blocked list**: plugins whose scan crashed, hung or failed, with the reason; **Retry** forgets one (or all) and scans again. One scan at a time; the buttons are disabled meanwhile. A scan that can't run (no helper) shows its error and caches nothing.
- The device pickers (chain and mixer) list its usable effects.
- An app launched by a tool (`AppOptions.isAutomated`: dawmcp, `dawctl --launch`) works on a copy of the user's cache in `$TMPDIR/EmberStudio-Plugins-<pid>/` (CONV §9), so parallel worktrees' apps never write one shared file.
- *Control ids (UI-052)*: `prefs.plugins` (toggle, always listed). While open: `prefs.plugins.close`, `prefs.plugins.scan`, `prefs.plugins.rescan`, `prefs.plugins.blocked.retry`, `prefs.plugins.blocked.<n>.retry` (the n-th blocked plugin), `prefs.plugins.blocked.<n>.retryLong` ("Retry (120 s)", timed-out plugins only; 10 "Contract delta (T-094)"); `ui.state` blocked rows carry `timedOut`. Generic plugin cards in the device chain show the plugin's display strings and menus/toggles from its steps and labels (08 "Contract delta (T-094)"). Accessibility identifiers that name views: `prefs.plugins.panel`, `prefs.plugins.summary`, `prefs.plugins.progress`, `prefs.plugins.error`, `prefs.plugins.available`, `prefs.plugins.blocked`.
- `ui.state` windows carry `pluginManager`: `{open, scanning, loaded, cachePath, scannerPath|null, lastScan{scanned, unchanged, removed}|null, error|null, plugins[{format, identifier, name, vendor, version, instrument, sidechain, numParams}], blocked[{n, format, identifier, name, reason}]}` (the lists stay empty until the cache was read: the panel opened or a picker needed it).

*Audio preferences details (clarified in T-055).* `AudioPreferencesModel` (`App/EmberStudio/Shell/Model/`), one per project window. *Export dialog details (clarified in T-082).* `ExportModel` (view model, one per window, `App/EmberStudio/Shell/Export/`) / `ExportPanel` (`Views/ExportView.swift`): a strip under the toolbar like the audio settings (in the layout, so `ui.snapshot` shows it and the AppKit canvases don't cover it). *One live engine (DW-156, clarified in T-090; docs/autobuild/DECISIONS.md "T-090 one engine").* With a realtime engine choice (`--engine fake|coreAudio`), the app has one live engine (`AppModel.liveEngine`). Only the main (front) window's project holds it, so only one window ever opens the device. Each other window keeps an offline engine of its own, so waveforms (peaks) and export keep working there. That engine is kept while the window lives, so its assets stay loaded. With `--engine offline` every window has its own offline engine, as before.
- *Handover*: when another window becomes main (focus, File > New/Open, closing the front window, which hands the engine to the window that comes forward), the steps are:
  - The transport stops. A take that was recording ends, and its `recordingFinalized` events go to the project that recorded it before the engine moves.
  - Hosted plugins' live state is carried over (captured from one engine, restored into the other, MODEL-043).
  - The project being left gets its offline engine back.
  - The live engine is attached to the new front project: engine sync re-applies params, graph, loop, arms and monitoring.
  - Only the assets that engine hasn't loaded yet are loaded.
  - The live engine is switched to the project's session rate. If the device can't run it, the project follows the engine (`SetSessionSampleRate`, DW-130) and a "Session rate changed" warning toast says so.
  - A running export (on either window's engine) holds the handover until it ends; the display-rate pump retries.
- *Control socket*: `project.new`/`open` replace the main window's project, which takes the live engine with it; the replaced project lets it go.
- `ui.state`: top-level `liveWindow` (id | null), per window `engine: {live, mode: realtime|offline} | null`.

*Monitoring feedback guard (DW-230, clarified in T-090; DECISIONS.md "T-090 feedback guard").* `auto` monitoring stays the default. `FeedbackGuard` (one per window, `Shell/Model/FeedbackGuard.swift`) warns when an audio track monitors its input and the engine's input is the built-in microphone while its output is the built-in speakers.

- *Which devices* (`AudioDeviceInfo.isBuiltIn`, 08 delta T-090): the input is the audio settings' input device, else the system default input (`isDefaultInput`). - *The warning*: a new risk posts a sticky warning toast, "Feedback risk", naming the tracks and devices. Its action, "Monitoring Off", sets those tracks' monitoring off through `SetMonitoring` (history-exempt). A risk counts as new when it wasn't there before, a track joins it, or the devices change. The toast goes when the risk ends. A dismissed warning comes back only for something new.
