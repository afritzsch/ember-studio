## Interfaces (contract)
```cpp
struct PluginDescriptorPOD { uint8_t format; /*au=0, vst3=1*/ std::string identifier; /* AU: type:subtype:manufacturer, VST3: path#classUID */
                             std::string name, vendor, version; bool isInstrument, hasSidechain; uint32_t numParams; };
```
Scanner stdout JSON = array of `PluginDescriptorPOD` fields + `{status: ok|blocked, reason?}`.

### Contract delta (T-061), accepted (autobuild, see docs/autobuild/DECISIONS.md "T-061 contract")
Additive; the facade side is in 08 "Contract delta (T-061)". How the AU half is hosted (`Sources/DAWEngine/plugins/`):
- **Identity and config.** `NodeKind::auPlugin`'s `configJSON` = `{"identifier", "state"?}`. The identifier follows the scanner's `AudioUnitIdentifier` (four-character codes, `0x` + 8 hex digits otherwise).
- **One AU per slot** (`AUPluginHost`). A slot's AU outlives node re-creations (configVersion bumps, a changed param range), so edits never reset its DSP or lose state; a new AU is made only for a new slot, a changed identifier, or a session-rate change (the new AU gets the old one's state). Instantiation runs on `daw.compile` (or the caller's thread for `instantiatePlugin`), in-process; an AUv3 that can't load in-process is loaded out of process (waits ≤ 10 s). The node is rendered only once `prepare` (formats, `maximumFramesToRender`, `allocateRenderResources`) has succeeded (PLUG-012).
- **Render** (PLUG-010): stereo bus formats where the AU accepts them (else mono, summed/duplicated), main input bus enabled, preallocated `AudioBufferList` and scratch buffers, `renderBlock` with a pull-input block; MIDI from `NodeIO::midiIn` through `scheduleMIDIEventBlock` at `AUEventSampleTimeImmediate + frameOffset`; host musical-context and transport-state blocks from the block's `TransportBlock`. No Objective-C message on the audio thread. Apple's AUDelay/AUSampler/AUMIDISynth render, schedule MIDI and take parameter events without allocating, so the RT trap needs no exemption.
- **Params** (PLUG-015): param slot *i* drives the AU parameter at index *i* of `parameterTree.allParameters` (listed by `pluginInfoJSON`). Slots whose generation moved are pushed at block start through `scheduleParameterBlock` (clamped; ramped over the block if the parameter can ramp). NaN = not set: the plugin keeps its value. The plugin→model direction (AU parameter observer → `SetParam`, gesture-coalesced) is left to T-063, where plugin-side edits first appear.
- **Latency** (PLUG-013): `latency` at prepare, then KVO; a change goes to the node's `LatencyReporter` from a global dispatch queue (MIX-024).
- **Sidechain** (PLUG-014, DW-159): the AU's aux input bus (bus 1) is enabled and fed from `NodeIO::sidechain` (graph `toPort` 0).
- **State** (PLUG-016): `fullState` ↔ binary plist, off the RT thread.
- **Lifecycle (DW-214, clarified at merge).** V2 AUs run behind Apple's `AUAudioUnitV2Bridge`, whose parameter tree follows render-thread parameter events asynchronously (a few ms), so `pluginInfoJSON` values lag them; and the bridge's listener crashes if the unit is destroyed while its messages are pending. So `AUInstance` stops KVO, render resources and host blocks first and drops a bridged unit's last reference 1 s later on a serial queue (AUv3 units are released at once), and one process-wide, non-RT lifecycle lock serializes prepare, teardown and release (CoreAudio aborts when one V2 AU initializes while another uninitializes).

### Contract delta (T-062), accepted (autobuild, see docs/autobuild/DECISIONS.md "T-062 contract")
Additive; the facade side is in 08 "Contract delta (T-062)". The VST3 half (`Sources/DAWEngine/plugins/VST3*`) mirrors the AU half of the T-061 delta:
- **Identity and config.** `NodeKind::vst3Plugin`'s `configJSON` = `{"identifier": "path#classUID", "state"?}` (the scanner's identifier, class UID as 32 hex digits, canonically uppercase; state as `getPluginState` returns it, base64).
- **One instance per slot** (`VST3PluginHost`), the same rules as `AUPluginHost`, including a failed load rendering as absent (`pluginCrashed`, the graph isn't rejected). Modules load and unload under one process-wide mutex.
- **Render** (PLUG-011): every bus the plugin declares gets channel buffers (`AudioBusBuffers`, unused buses too); main in/out stereo where accepted, else mono (mono output duplicated). All process inputs (scratch buffers, `ProcessData`, event/param lists, `ProcessContext`) are preallocated in `prepare`. Fixed-capacity `IEventList` and `IParameterChanges` of our own, with `addEvent`/`addPoint`/`addParameterData` allocation-free, since the SDK helpers grow vectors. `ProcessContext` from `TransportBlock`: tempo, ppq, bar position, time signature, playing, continuous time. Notes in `NodeIO::midiIn` become note on/off events at their frame offsets (other MIDI: T-063/discovered work). The audio thread calls the plugin only through the `IAudioProcessor` vtable; RT safety of plugin code is verified by the RT trap, not assumed.
- **Params** (PLUG-015): param slot *i* drives the *i*-th parameter of `IEditController::getParameterInfo`. One point per block at offset 0 (D-13), clamped to 0…1. **VST3 values are normalized:** `pluginInfoJSON` reports `min 0, max 1, canRamp false`, and the model/automation see normalized values. NaN = not set. Read-only parameters (meters) aren't pushed. Pushed values are written to the controller off the RT thread before `params(true)`/`state()` read it. The plugin → model direction is T-063 (DW-204): `IComponentHandler::performEdit/beginEdit/endEdit` are accepted no-ops.
- **Latency** (PLUG-013): `getLatencySamples()` at prepare; `restartComponent(kLatencyChanged)` from any thread only sets an atomic flag, and a 50 ms timer on a utility queue re-reads latency off the RT thread and reports it through the node's `LatencyReporter` (MIX-024).
- **Sidechain** (PLUG-014, DW-159): the first `kAux` audio input bus is activated and fed from `NodeIO::sidechain` (graph `toPort` 0).
- **State** (PLUG-016): one blob: magic `EVS3`, u32 version 1, u64 component length, component state, u64 controller length, controller state (little-endian), through `MemoryStream`, off the RT thread. Restore calls `IComponent::setState`, then `IEditController::setComponentState` and `setState`.
- **Editor seam** (T-063): `VST3Instance::editController()` is the `IEditController` for `createView`; `EngineFacade::createPluginView` is still a stub.

### Contract delta (T-064), accepted (autobuild, see docs/autobuild/DECISIONS.md "T-064 bypass", "T-064 crash marker", "T-064 NaN event")
Additive; the facade side is in 08 "Contract delta (T-064)".
- **Host bypass** (PLUG-018, `graph/BypassNode.h`). A node whose `NodeDesc` has a `bypassParam` (05 `GraphDescription`, a defaulted additive field) is wrapped by `GraphBuilder` in a `BypassNode` made for each graph around the pooled node, so bypass never re-creates the device or touches its state. While the slot is ≥ 0.5 (NaN: not bypassed) the device isn't processed; the wrapper outputs its main input delayed by the device's `latencySamples()` as the build read it, the latency PDC planned with, so every path keeps its alignment and toggling is a slot write, never a rebuild. An instrument has no main input, so bypassed it is silent; MIDI and the sidechain reach the device only while it runs. A toggle crossfades linearly over one block (D-13). The delay line runs every block and is kept per NodeID across rebuilds (like MIX-022's), replaced by a silent one only when a grown latency no longer fits. This is generic: built-in devices get it too.
- **Model** (07, MODEL-005): the undoable `SetDeviceBypass {slotID, bypass}`. Every device slot (instrument or insert, built-in or plugin) gets one bypass param slot, keyed `GraphNodeID.bypass(of: slot)` (role 5) in `RuntimeIDs`, and bypassed devices stay in the graph, so `GraphDescriptionBuilder.paramValues` writes bypass as a value (1 / 0). Closes DW-098 and the bypass part of DW-149.
- **NaN guard** (PLUG-022, `plugins/PluginNanGuard.h`): after each rendered block an AU or VST3 node checks its output; a block with any non-finite sample becomes silence, counts in telemetry `nanBlocks` (T-070's counter) and raises the node's `PluginHealth`. `AUPluginHost`/`VST3PluginHost::takeMisbehaved()` reports each raised health once (a fresh health per node instance) and the facade turns them into `pluginMisbehaved{slot}` events. The plugin keeps running, so one that recovers plays again.
- **Crash policy** (PLUG-020): no sandbox (D-07); the autosave (MODEL-044/045) is the mitigation, unchanged. **PLUG-021**: `CrashMarkerSession` (DAWModel) writes `running-<pid>.json` to `~/Library/Application Support/Ember Studio/` at launch (automated app launches: `$TMPDIR/EmberStudio-Sessions/`), listing the open projects (name, folder) and their AU/VST3 slots (slot, format, identifier, name); it is rewritten when that changes (checked every 2 s) and removed on a clean quit (`end()`). One file per process, so concurrent instances don't collide (CONV §9). A marker whose pid is gone was left by a crash: `start` returns those as `crashedSessions` (and removes their files), `CrashMarker.leftByCrashedSessions(in:)` lists them. The app calls `start` in `applicationDidFinishLaunching` and `end` on terminate; the dialog is T-083. **Safe mode** is `ProjectStore.isSafeMode` / `ProjectStore.open(_:recover:safeMode:)` (and `EngineSync.arePluginsBypassed`): a session-only override that host-bypasses every AU/VST3 slot from the first graph on, keeping slots, params and state; nothing is written to the document (no undo entry, not dirty); built-ins keep their own bypass. Plugins are still instantiated in safe mode (a plugin that crashes on instantiation isn't protected; see the T-064 report).

### Contract delta (T-063), accepted (autobuild, see docs/autobuild/DECISIONS.md "T-063 editors")
Additive; the facade side is in 08 "Contract delta (T-063)", the app side in 12 "Plugin editor details".
- **Editors** (PLUG-017, `plugins/PluginViewHost.{h,mm}`). One editor per device slot, a container `NSView` the facade owns. It holds the slot's current plugin instance (its latest node's, else a parked one), so the plugin can't go away under its view. Main thread only.
  - **AU:** `requestViewController`. A unit that answers nil, or doesn't answer within 2 s, gets CoreAudioKit's `AUGenericViewController`. The controller arrives on the main queue, so the container starts at 400 × 300 and takes the view's preferred size (else its frame, else its fitting size) when it comes.
  - **VST3:** the controller's `createView("editor")` attached as `kPlatformTypeNSView`, at its `getSize`. `IPlugFrame::resizeView` sets the container's frame, then calls `onSize`. A resize of the container from outside reaches a view that `canResize` through `checkSizeConstraint` and `onSize`. While a VST3 editor is open, a 30 Hz main-queue timer writes the model's values into its controller (`VST3Instance::syncEditor`), so undo and automation show.
  - **Replaced instance:** an editor whose slot got a new instance (a session-rate change) reports `stale`, and opening it again shows the new one.
- **Test plugin** (DW-208). EmberTest's controller has its own `IPlugView` (`Tests/VST3TestPlugin/EmberTestView.mm`): a plain NSView, 400 × 300, resizable down to 200 × 150, drawing the gain as an orange bar. vstgui4 isn't fetched, so `again` keeps its stub view.
  - New test exports: `ember_test_edit` (begin/perform/endEdit as a knob does), `ember_test_controller_param`, `ember_test_view_info`, `ember_test_view_request_resize`.
- **Plugin → model** (PLUG-015 second half, DW-204, `plugins/PluginEditQueue`). A plugin's own edits go to the facade's queue as edits of the slot's param *index*. The facade turns them into `pluginParamEdited` events, and the model turns them into undoable `SetParam` gestures (07, `PluginEditRecorder`).
  - **VST3:** `IComponentHandler::beginEdit/performEdit/endEdit`. Nested begins count once; an end without a begin and unknown ParamIDs are refused. A begin carries the controller's value before the gesture.
    - While the editor's gesture is open, controller sync skips the param, and also after it until the model's slot value matches the editor's newest value (at most 1 s). The knob never jumps back to an older model value.
    - The processor still gets the model's value through the slot, one poll later.
  - **AU:** the parameter tree's automation observer (Touch → begin, Value, Release → end; a Value outside a gesture is ungestured). The observer follows the unit's *current* tree: a V2 bridge builds a new one when it is prepared or its state is set.
    - The echo of a host push (the bridge reports render-thread parameter events back) matches one of the last 16 pushed values and isn't an edit.
    - `AUInstance::pushDecision` (RT, atomics only) keeps the node from fighting the editor:
      - while the param's gesture is open, its push is *deferred* (retried each block);
      - after a release or an ungestured edit, the plugin's value is *held* until the model's value matches (that push is *skipped*: the plugin has it) or 300 ms pass.
- **Undo of a first edit** (docs/autobuild/DECISIONS.md "T-063 first-edit undo", option (c)). A gesture's `begin` on a param the document doesn't set carries the plugin's value before the gesture.
  - `PluginEditRecorder` hands that value to `EngineSync`, which remembers it for the session as the param's *baseline*: the newest such begin wins, and it is kept while the slot is out of the project, since undo and redo can bring it back.
  - While the document leaves the param unset, EngineSync writes the baseline to the param's slot instead of NaN ("not set"), and keeps a slot for it.
  - So undoing a first plugin-side edit is still one undo entry, the document goes back to unset, and the plugin goes back to its own value. A later set (redo, another control, automation) works as before.
  - Ungestured edits (no `begin`) have no baseline: undoing one leaves the plugin at the edited value.

### Contract delta (T-083), accepted (autobuild, see docs/autobuild/DECISIONS.md "T-083 safe mode slots")
Additive; the facade side is in 08 "Contract delta (T-083)", the dialog in 12 "Crash recovery details". Closes DW-224.
- **Safe mode builds plugin slots without their plugin** (PLUG-021, option (a)). It supersedes the last sentence of the T-064 delta ("Plugins are still instantiated in safe mode"). While `ProjectStore.isSafeMode` is set, every AU/VST3 slot's `configJSON` carries `"disabled": true` (`GraphDescriptionBuilder.build(_:runtime:pluginsDisabled:)`, set by `EngineSync` from `arePluginsBypassed`). `AUPluginHost`/`VST3PluginHost` build such a slot as **absent**: an effect passes its input through, an instrument is silent, and the plugin is never instantiated, its module never loaded, its state never applied. So a plugin that crashes on load, prepare or state restore can't take the app down.
  - **No failure.** A disabled slot reports no `pluginCrashed` (nothing was tried). `pluginInfoJSON` answers `{"slot", "identifier", "loaded": false, "disabled": true}`. The editor seam (`current`) has no instance, so `createPluginView` returns null.
  - **State.** The host keeps the configured state, so `getPluginState` returns the stored blob and a save in safe mode writes it back byte for byte. A state set while disabled is held for the slot's first instance; an instance that still exists is kept for when the slot is enabled.
  - **The document is untouched**: slots, params, bypass and state blobs. Safe mode is session-only: no undo entry, not dirty. The host bypass of T-064 is still written as well, so the in-graph bypass path is unchanged.
  - **Toggling.** Turning safe mode on or off changes the plugin slots' config strings. The nodes are re-created (`configVersion` bump, DW-140) and the graph is re-applied (debounced like any structural change). Turning it off instantiates the plugins as on a normal open, and a missing one then reports `pluginCrashed`. Enabling single slots stays a separate item (DECISIONS "T-083 safe mode slots").
- **Recovery check** (MODEL-045, UI-043): `ProjectStore.hasNewerAutosave(at:)` (nonisolated, static) says whether a folder's `autosave/project.json` is newer than its `project.json`, or exists without one. It reads modification dates only, so the dialog can offer recovery before opening anything.
- **Running marker directory**: the app's `--crash-marker-dir <path>` (12 "Crash recovery details") names where `CrashMarkerSession` reads and writes markers.

### Contract delta (T-094), accepted (autobuild, see docs/autobuild/DECISIONS.md "T-094 plugin info")
Additive; the facade side is in 08 "Contract delta (T-094)". Closes DW-213, DW-275, DW-018 and DW-276; DW-268 is in the T-094 report.
- **PLUG-001 (updated).** The scanner gets **30 s** for a first scan (was 10 s; DW-275: FabFilter, AmpliTube, Komplete Kontrol and MODO need more on their first load, licence checks included). A crash, a timeout or unusable output still marks the plugin `blocked` with a reason; a timeout's reason is "timed out after N s" (`PluginDescriptor.isTimedOut`).
  - **Retry with a longer limit.** `PluginScanning.scan(_:timeout:)` scans with a limit of its own (a default implementation ignores it, so fakes compile unchanged). `PluginCatalog.retryBlocked(identifiers:timeout:)` forgets those blocked plugins and refreshes; only they get `timeout`, other new or changed candidates the scanner's own limit. The plugin manager offers "Retry (120 s)" (`ScannerLauncher.retryTimeout`) for each timed-out plugin (12 "Plugin manager details").
  - **Parallel scans (DW-018).** `refresh` runs up to `PluginCatalog.maxConcurrentScans` (4) scanner processes at once, still one per candidate, so a hanging plugin holds one worker for its timeout. The cache and the refresh summary keep discovery order. The first "scanner can't run" error stops handing out work and is thrown; nothing is cached then, as before.
- **Discrete params and display strings (PLUG-015, DW-213).** VST3 values stay normalized 0…1 in the model and in automation (plain units would change what saved automation means). Each plugin parameter also reports:
  - `steps`, as 06's `ParamInfo::steps`. VST3: `ParameterInfo::stepCount`. AU: 1 for a Boolean parameter; max − min for an Indexed one, or for one whose `valueStrings` name every integer of its range; else 0.
  - `labels`: steps + 1 value names in value order, for steps ≤ 128. VST3: `getParamStringByValue(k / steps)`. AU: `valueStrings`, else its string for each step if the parameter has `kAudioUnitParameterFlag_ValuesHaveStrings`.
  - `display`: the plugin's own string for the current value, without the unit. VST3: `getParamStringByValue`. AU: a step's label, else its string-from-value if it has strings, else none (the host formats the number).
  - Labels are read once per instance on the first info read, not at instantiation (which runs on `daw.compile`). An AU parameter without a `unitName` gets its unit's symbol (Hz, dB, ms, %, …).
- **AU edit observer follows the tree (DW-204, DW-276).** A V2 bridge can replace its parameter tree after the step that caused it has returned (seen after prepare under heavy load), and the automation observer stayed on the dropped tree, so an editor's gestures were lost. `AUInstance` now also follows `AUAudioUnit.parameterTree` by KVO. The observer state is shared and has its own lock, and teardown closes it, so a late callback is harmless.
