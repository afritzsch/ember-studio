# 13 — Control Protocol, `dawctl`, `dawmcp`

**Depends on:** 07 (Commands, ProjectStore), 08 (EngineClient) · **Owns:** `Sources/DAWControl/`, `Sources/dawctl/`, `Sources/dawmcp/`, `App/EmberStudio/Control/` (socket server).

Agents use this to **drive and verify the DAW themselves** (D-20, D-21, D-22). There is one protocol and three transports:

```
           ┌─────────────── DAWControl (JSON-RPC 2.0 types + Dispatcher) ───────────────┐
 dawctl ───┤ headless: in-process ProjectStore + EngineClient(.offline)                  │
 dawmcp ───┤ headless: same, OR attach: Unix socket → running app's Dispatcher           │
 App    ───┤ ControlSocketServer at a per-instance socket path (CTL-032)                 │
           └──────────────────────────────────────────────────────────────────────────────┘
```

**Protocol details (clarified in T-017).** The code is the reference: `Sources/DAWControl/ControlParams.swift` (params/results), `ControlError.swift` (codes).
- *Wire:* named params only (an object; missing = `{}`); a request without `id` is a notification; a JSON array is a JSON-RPC batch. Relative paths resolve against the dispatcher's working directory (dawctl: its cwd).
- *Errors (CTL-003):* `data = {dawError, detail, …}`. Codes: -32700 `parseError`, -32600 `invalidRequest`, -32601 `methodNotFound`, -32602 `invalidParams`, -32603 `internalError`, -32000 any `DAWError` (`data.dawError` is its case, `data.error` its JSON, a cycle adds `data.path` in model IDs; engine NodeIDs are mapped back with `GraphNodeID.owner(of:)`), -32001 `methodNotAvailableInHeadless`, -32002 `noProject`, -32003 `timeout`. Batch and fixture failures add `index`/`results` or `line`.
- *Determinism (CTL-004, DW-033):* headless `project.new` number *n* gets project ID `00000000-0000-0000-0000-<n in hex>`; headless engine sync applies structural changes synchronously (debounce 0).
- *`command.apply`* returns `createdIDs`: the entity IDs present after and not before. *`command.batch`* `atomic: true` is one `CompositeCommand` (all or nothing); `atomic: false` (default) performs each as its own undo entry and stops at the first failure.
- *`transport.*`* act on the engine. `transport.setLoop {enabled, start?, end?}` also performs `SetLoop` first (DW-123; one undo entry, SetLoop's checks apply, a refused loop never reaches the engine), so `project.loop` follows; `enabled: false` without a range clears it (`loop: null`). The dispatcher also sets the engine directly; since T-031 engine sync pushes `project.loop` on every change too (DW-123), so the engine may get the same loop twice. `transport.wait` needs a realtime engine; headless is offline, so it returns `invalidArgument` there.
- *`transport.setMetronome`* (T-026, TIME-010; accepted (autobuild, see docs/autobuild/DECISIONS.md)) `{enabled?, level?, accent?}` performs `SetMetronome` (07): fields left out keep their value, at least one is needed, levels are linear 0…+12 dB (default level 0.25, accent 2). It marks the project dirty but isn't undoable, so `undo` steps over it. It returns `project.metronome`. The engine sees slot writes on the metronome node, never a rebuild. dawmcp: `daw_transport_set_metronome`.
- *`asset.import`* loads the file into the engine under the next model ID, waits for the job, then performs `{"type": "ImportAsset", "asset": AssetRef}` (MODEL-005); until that command exists it returns `notImplemented`.
- *`project.save` / `project.open` (T-031, DW-107):* `project.save {path?}` writes the project folder (MODEL-040). `path` is used as given; the default is where the project was opened or last saved, and a new project without one gets `invalidArgument`. Audio outside the folder is copied into `Audio/` (DW-124). `project.open {path, recover?, engine?}` opens the folder, installs the engine, loads every asset relative to the folder (`ProjectStore.loadAssets`) and returns `{loadReport}`, DAWModel's `ProjectLoadReport`: `{offlineAssets, migratedFrom?, recovered, recoveryAvailable, repairs}`. `recover: true` opens a newer autosave (MODEL-045); dawctl passes it as the param, as in `dawctl project.open --json '{"path": …, "recover": true}'`, not as a separate flag. File errors are `fileIO`; files that are unreadable, from a newer format or invalid are `invalidProject`. Headless stores don't autosave (`autosavePolicy = nil`), so dawctl and dawmcp leave no `autosave/` behind. Attach mode keeps the app's policy.
- *`render.offline`* `{from, to, path, format? (wav|caf|aiff), sampleFormat? (float32|int24|int16), tail? = true, blockSize? = 512, loop? = false}` flushes pending engine sync and waits for the graph build first (DW-095); a rejected build is an error. The result adds `sampleRate`, `frames`, `rtViolations`, `clippedSamples`. `loop: true` (T-036, accepted (autobuild, see docs/autobuild/DECISIONS.md)) keeps the transport's loop (`transport.setLoop`): the render is the range's length of playback from `from`, wrapping at the loop end like live playback (`ExportSpecPOD.followLoop`, 08). The default plays the range straight through with the loop off, as before. `includeMetronome? = false` (T-026, accepted (autobuild, see docs/autobuild/DECISIONS.md) Q1): exports leave the project metronome's click out unless this is true. The `on` slot is held at 0 for the render only (`EngineSync.isMetronomeSuppressed`), so it is a slot write, not a rebuild, and live playback afterwards clicks as before. With the metronome off, `true` adds nothing. No facade change: `ExportSpecPOD` is untouched.
- *`audio.analyze`* `range` is file frames `{start, end}`; silence reads -240 dB (JSON has no -∞); LUFS is BS.1770-4 with every channel weighted 1; true peak is 4× oversampled; `spectrum` is `bands` (default 32) log bands of `{lowHz, highHz, db}` from 20 Hz, a full-scale sine reading 0 dB, plus `spectrumPeakHz`; `dcOffset` is the largest channel mean; `firstNonSilentSample` is -1 when silent (threshold `silenceThresholdDb`, default -120).
- *`audio.compare`* `nullResidualDb` is the peak |a − b| in dBFS (shorter file zero-padded), `pass = nullResidualDb ≤ toleranceDb` (default -100, TEST-002); `offsetSamples > 0` means b is later than a (search ±`maxOffset`, default 1 s, first 2^20 frames).
- *`engine.telemetry`* `rtViolations` = engine render scope + every offline render's own scope (also reported apart); `nodeLatencies` carry `owner` and `role`; `graph` is the build status. *`engine.events`* `{since}` → `{events: [{seq, event}], next}`; events are drained once, before every request.
- *`test.fixture`* runs `<name>.jsonl` from the fixture folders (dawctl: `--fixtures`, `$DAWCTL_FIXTURES`, then `Tests/GoldenTests/fixtures` of its checkout), skipping `render.offline`, `audio.*` and nested `test.fixture` lines.
- *Engines and devices (DW-115, T-018):* `project.new`/`project.open` take `engine?: {mode? (offline|realtime, default offline), driver? (fake|coreAudio, default fake), outputDevice?, bufferFrames? = 256}`; realtime runs at the project's session rate through `Configuration.makeRealtimeEngine` (`makeEngine` still makes offline engines). `device.list` → `{devices, outputDeviceID, driver}` (driver null offline). `device.set {outputDevice?, inputDevice?, sampleRate?, bufferFrames?}` calls `setDevice` with the engine's driver kind (realtime only, else `invalidArgument`; a device that is gone is `engine`/`notFound`). `device.simulate {kind: deviceLost|deviceRestored|sampleRateChanged|processorOverload, deviceID?, sampleRate?}` calls `simulateDeviceEvent` (fake driver only, else `notImplemented`). Both return `{outputDeviceID, deviceRunning, sampleRate, events}`, the events being the ones the call raised; they are also kept for `engine.events`, where `deviceChanged` carries `device: {reason, previousDeviceID, deviceID, previousSampleRate, sampleRate}`. Telemetry has `outputDeviceID`, `processorOverloads`, `renderOverruns`.
- *Scripts (CTL-010):* one request per line, as JSON (`jsonrpc` optional, `id` defaults to the line number) or shorthand `method {params}`; `#` and `//` lines are comments. `dawctl script` stops at the first error unless `--keep-going`. Exit status (CTL-012): 0 ok, 1 a request failed, 2 bad usage.

**Attach mode details (clarified in T-032).** The code is the reference: `Sources/DAWControl/Socket/`, `Sources/DAWControl/Attach/`, `Sources/dawmcp/SessionMode.swift`, `App/EmberStudio/Shell/Control/`.
- *Socket (CTL-030/032):* newline-delimited JSON-RPC as above. Socket files are created 0600, and each peer must have the same uid (`getpeereid`). A socket file nobody answers on is unlinked when the server starts. A path where a server still answers, or a path that isn't a socket, is refused (`attachFailed`). The server removes only a socket file it created. The app serves when given `--control-socket <path>`, or in Debug at `$TMPDIR/emberstudio-<pid>.sock`. A path longer than `sun_path` allows (103 bytes) falls back to `/tmp/<same name>`. The attach path is `$TMPDIR/emberstudio-<first 8 bytes of SHA-256 of the checkout root, hex>.sock`.
- *Errors:* -32004 `attachFailed` means attach mode couldn't launch or reach the app, or the app closed the connection. An error the app returns arrives unchanged (the client's `remote` case).
- *Progress (CTL-031):* while a request with an `id` runs, the server sends the notification `{"jsonrpc": "2.0", "method": "progress", "params": {"id": <request id>, "method": <control method>, "progress": 0…1, "message"?}}` on the same connection, before the response. Render and asset jobs report at least 1 % apart, at most every 50 ms, and end at 1. dawmcp forwards progress as MCP `notifications/progress` `{progressToken, progress, total: 1, message: <method>}` when the tool call carries `_meta.progressToken` (DW-133), and sends all of it before the result.
- *App arguments:* `--control-socket <path>`, `--engine fake|coreAudio|offline` (default `coreAudio`; it is the engine `project.new`/`project.open` use when they don't ask for a mode; `fake` is realtime on the fake driver), and `--parent-pid <pid>` (quit when that process exits). With `--control-socket` or `--parent-pid` the app is "automated": quitting never asks about unsaved changes. SIGTERM is a clean quit: every project is `close()`d and the socket file is removed.
- *Launcher (CTL-023, DW-046):* the app is `<root>/.build/xcode/Build/Products/Debug/Ember Studio.app/Contents/MacOS/Ember Studio`. It is rebuilt with `xcodebuild … -derivedDataPath .build/xcode` when it is missing or older than anything under `App/EmberStudio`, `App/EmberStudio.xcodeproj` or `Sources/`, or than `Package.swift`/`Package.resolved` (log: `.build/attach/xcodebuild.log`). It is started with `Process` and an argument array (never a shell, never `open -a`) as `--control-socket <path> --engine <e> --parent-pid <launcher pid>`, with its output in `.build/attach/app.log`. An app already answering on the socket is reused and never stopped by this launcher. Stopping is SIGTERM, then SIGKILL after 3 s.
- *`daw_session_mode` (CTL-023):* `{mode: headless|attach, engine? = fake, build? = true}` returns `{mode, socketPath?, pid?, launched?, note?}`. In attach mode every other `daw_*` tool goes over the socket. Asking for attach again while connected returns `note: "already attached"`. `headless`, and the end of the MCP session (stdin closed), stop the app this session launched. Headless mode keeps its own in-process dispatcher throughout.
- *`dawctl` (CTL-011):* `--attach` uses this checkout's attach socket and `--socket <path>` an explicit one. `--launch` (with `--attach`) starts the app if nothing listens, without `--parent-pid`, so it outlives dawctl. `--progress` prints `dawctl: <method> <n>%` lines to stderr. `dawctl serve [--control-socket p] [--engine e] [--parent-pid n]` serves a headless dispatcher behind the same socket server (used as the app's stand-in in tests).
- *`ui.*` in the app (UI-050..052):* they act on the main window. `ui.state` is the UIStateDumper JSON: `{mainWindow, windows: [{id, title, isMain, project, panes, selection, zoom, scroll, visibleTracks, tracks, transport, toasts, controls}]}`. `ui.perform {accessibilityId, action}` runs a view model's control descriptor: `click`/`press` for buttons and toggles, `toggle`/`on`/`off` for toggles. It returns `{accessibilityId, kind, action, isOn?}`. An unknown id or a bad action is `invalidParams` (the message lists the ids); a disabled control is `invalidArgument`. Ids: `transport.play|stop`, `edit.undo|redo`, `zoom.in|out`, `pane.browser|inspector`, `pane.bottom.<mixer|pianoRoll|deviceChain>`, `track.<id>.select|mute|solo`, `toast.<n>.dismiss|action`; arrange (T-033): `snap.off|bar|beat|8|16|32|4t|8t|16t|32t`, `edit.selectAll|deselectAll|duplicate|split|delete` (split: selected clips at the playhead), `clip.nudge.left|right` (one snap step, a beat with snap off), `clip.nudge.up|down` (adjacent track of the same kind), `clip.<id>.select` (visible clips); toolbar and shortcuts (T-034, UI-002): `transport.playStop` (Space), `transport.record` (R; arms the transport's record state), `transport.loop` (L; toggles `project.loop` through `SetLoop`, creating 4 bars from the playhead's bar, or a loop around the selected clips, when there is none), `track.add.audio|midi` (⌘T, ⇧⌘T), `transport.metronome` (TIME-010: toggles `project.metronome.enabled` through `SetMetronome`, which marks the project dirty but isn't undoable; no shortcut). `ui.state` windows also carry `toolbar`: `{position (bars.beats.ticks), time, tempo, signature, loop{enabled,start,end}|null, metronome, dspLoadPercent, xruns}` and `keyBindings`: `[{keys, control}]` (every shortcut is a control id above). They also carry `arrange`: `{snap, pixelsPerBeat, size, visibleTicks{from,to}, visibleRows{from,to}, clipCount, visibleClips[{id, track, kind, start, length, selected, rect, …}], selection, marquee, gesture, playhead{tick,x}}`. Panels documented in 12 add their own ids and `ui.state` objects (DW-188, DW-195): the piano roll (`pianoRoll.*`, `windows[].pianoRoll`; 12 *Piano roll details*), the audio settings (`prefs.audio*`, `windows[].audioPreferences`; 12 *Audio preferences details*), the mixer (`mixer.*`, `windows[].mixer`; 12 *Mixer details*), the export dialog (`export.*`, `windows[].export`; 12 *Export dialog details*) and the track header's arm/monitor/input menus (`track.<id>.arm|monitor.*|input.*`; tracks carry `armed`, `inputPair`, `monitoring`, `monitoringLatency`). Later panels add theirs the same way: the device chain (`deviceChain.*`, `windows[].deviceChain`; 12 *Device chain details*), the plugin manager (`prefs.plugins.*`, `windows[].pluginManager`; 12 *Plugin manager details*), the crash recovery dialog and safe mode (`crashRecovery.*`, `safeMode.enablePlugins`; top-level `crashRecovery`, per-window `safeMode`; 12 *Crash recovery details*), take folders (`takeFolder.*`, `windows[].takes`; 12 *Take folders*) and the MIDI input picker (`track.<id>.midiInput.*`; 12 "Contract delta (T-093)"). `ui.perform` also takes optional `start`/`end` (ticks), used only by `action: "swipe"` on a take (`takeFolder.<id>.take.<take>.swipe`, 12 *Take folders*). 12 is the source of truth for those lists. `ui.snapshot {path?}` writes the main window's content view through `cacheDisplay` (with the arrange canvas's Metal waveforms rendered offscreen and composited over it, T-033) to `path` (relative to the app's working directory; default `$TMPDIR/emberstudio-<pid>-snapshot-<n>.png`) and returns `{pngPath, width, height, window}`.

**dawmcp details (clarified in T-018).** The code is the reference: `Sources/dawmcp/DawTools.swift`, `Sources/DAWControl/Schema/`.
- *Tools (CTL-021):* one per `ControlMethod`, named `daw_` + the method with `.` → `_` and camelCase → snake_case (`transport.setLoop` → `daw_transport_set_loop`). `inputSchema` is generated from the method's `paramsType` by `JSONSchema.of` (a probing decoder; types it can't see through, i.e. tagged unions and non-`CaseIterable` string enums, conform to `JSONSchemaDescribing` in `Schema/ModelSchemas.swift`). A result is one text item with the result JSON; a failure sets `isError` and its text is the JSON-RPC error object (`{code, message, data}`, CTL-003). `daw_ui_snapshot` puts the PNG first as image content, then the `{pngPath}` text (CTL-022).
- *Command catalogue (CTL-024):* the control method `command.schema` (so `dawctl` has it too) lists `CommandRegistry.registered` with each command's wire-form schema (`type` as a `const`).
- *Process (CTL-020):* SDK `modelcontextprotocol/swift-sdk` pinned `exact:` in `Package.swift` (+ `Package.resolved`). stdout carries only MCP frames (fd 1 is redirected to stderr at start). The server exits when stdin closes. Headless config as `dawctl` (fixtures: `--fixtures`, `$DAWCTL_FIXTURES`, the checkout's `Tests/GoldenTests/fixtures`).
- *Launcher (CTL-025):* `.mcp.json` runs `sh -c 'exec "$(git rev-parse --show-toplevel)/scripts/dawmcp.sh"'`. The script builds `--product dawmcp` (output to stderr) when `.build/debug/dawmcp` is missing or older than `Package.swift`, `Package.resolved` or anything under `Sources/`, then execs it with the checkout root as its working directory, so relative render paths land in that worktree. `scripts/dawmcp.sh --build-only` pre-builds (a fresh worktree's first build takes minutes, longer than an MCP client waits).

### Contract delta (T-056, accepted (autobuild, see docs/autobuild/DECISIONS.md))
Additive. No new method: the session rate changes through `command.apply {"command": {"type": "SetSessionSampleRate", "sampleRate": 96000}}` (07, history-exempt, so `undo` steps over it), or follows the engine after `device.set`/`device.simulate` (DW-130: the dispatcher's event drain makes the store perform it). `engine.events` (and the `events` of `device.*` results) carry `reload: {phase: started|progress|finished, previousSampleRate, sampleRate, done, total, failed, assetID}` on `assetsReloaded` events (DW-044); `engine.telemetry` has `assetsReloadPending`. `render.offline` after a rate change waits for the re-conversion (in the engine), so a render hears the new assets.

### Contract delta (T-052), accepted (autobuild, see docs/autobuild/DECISIONS.md "T-052 contract")
Additive. New method `transport.setPunch {enabled, start?, end?}` (REC-005): `enabled: true` needs `0 ≤ start < end` (left-out bounds come from the current range), otherwise `invalidArgument`. `enabled: false` keeps the range or stores one given with both bounds (one bound alone is `invalidParams`). It returns the transport state, which now carries `punchEnabled`, `punchIn` and `punchOut`. Tool: `daw_transport_set_punch`. `transport.record` goes through `EngineSync.setRecording` (the recordings folder first, 09). `transport.stop`, `transport.record` and `transport.locate` drain events before answering, so a finished take is already a clip when they return. `render.offline` also waits for imported takes to load. `engine.events` carry `recording: {track, file, startSample, frames, takeIndex, channels, sampleRate, inputPair, droppedFrames}` on `recordingFinalized`. `engine.telemetry` has `recordDrops`, `deviceInputLatency` and `armedTracks`. Arming and monitoring are commands: `command.apply {"command": {"type": "ArmTrack", "trackID": 2, "armed": true, "inputPair": 0}}` and `SetMonitoring`.

### Contract delta (T-053), accepted (autobuild, see docs/autobuild/DECISIONS.md "T-053 contract")
Additive. New methods `midi.inputs` → `{inputs: [{uniqueID, name, connected}]}` (REC-010: CoreMIDI sources; empty on offline and fake-device engines) and `midi.inject {events: [{sample | framesFromNow, status, data1?, data2?}]}` → `{accepted}` (T-053's test seam, realtime engines: messages arrive as if from a connected MIDI source; give exactly one of `sample`, a transport sample, or `framesFromNow`). Tools: `daw_midi_inputs`, `daw_midi_inject`. MIDI tracks are armed with `ArmTrack` too (`inputPair` is ignored). `transport.stop` and friends also import MIDI takes before answering. `engine.events` carry a MIDI take as `recording: {…, endSample, notes: [{start, end, pitch, velocity, channel}]}`; `engine.telemetry` has `midiInputDrops` and `armedMidiTracks`.

### Contract delta (T-061), accepted (autobuild, see docs/autobuild/DECISIONS.md "T-061 contract")
Additive. New method `engine.pluginInfo {slot}` (PLUG-010/015): the engine's `pluginInfoJSON` for a device slot's hosted plugin, `{slot, identifier, loaded, error?, name, instrument, midi, sidechain, inputChannels, outputChannels, latencySamples, tailSeconds, params: [{index, address, id, name, unit, min, max, value, canRamp}]}` (08, 10 Contract delta (T-061)). A slot the engine has never seen answers `{slot, loaded: false}`. Tool: `daw_engine_plugin_info`. Hosted plugins are placed with `SetInstrument` (`"device": {"format": "au", "identifier": "aumu:samp:appl", "name": …, "vendor": …, "version": …}`). `project.save` writes each hosted slot's live state to `Plugins/<slotID>.state` (MODEL-043): the dispatcher installs `EnginePluginStates` as the store's `pluginStateProvider`.

### Contract delta (T-062), accepted (autobuild, see docs/autobuild/DECISIONS.md "T-062 contract")
Additive. `SetInstrument` (and `RestoreTrack`/`RestoreBus` inserts) take `"device": {"format": "vst3", "identifier": "path#classUID", "name": …, "vendor": …, "version": …}`. `engine.pluginInfo` answers VST3 slots with the T-061 shape (`address`/`id` = ParamID, `min` 0, `max` 1, values normalized). `project.save` writes each VST3 slot's state (`EVS3` container, 10 Contract delta (T-062)) to `Plugins/<slotID>.state`.

### Contract delta (T-089), accepted (autobuild, see docs/autobuild/DECISIONS.md "T-089 queued play"; pre-accepted in T-089's briefing)
Additive. The transport state every `transport.*` method returns carries `playPending` (`TransportState.playPending`, 08 "Contract delta (T-089)"): `transport.play` during an asset re-conversion after a session-rate change (IO-033) answers with `playing: false, playPending: true`, and the transport starts by itself when the re-conversion finishes; `transport.stop` cancels it. `render.offline` renders are bit-identical on one engine whatever played before (DW-063: every node is reset first), and with `loop: true` a loop shorter than `blockSize` wraps as often as it comes (DW-125) instead of leaving a gap. A tempo edit (`SetTempo`, …) keeps the playhead's tick (DW-061).

### Contract delta (T-082), accepted (autobuild, see docs/autobuild/DECISIONS.md "T-082 normalize")
Additive. `render.offline` takes `normalize? = false` (UI-042): the export is scaled by one gain so its sample peak is −0.1 dBFS, applied before quantization (`ExportSpecPOD.normalize`, 08), up or down; silence stays as it is. With it the result adds `normalizeGain` (linear; absent without `normalize`). The default renders exactly as before. Golden: `export_normalize`. In the app, `ui.perform` drives the export dialog (`export.*`, 12 *Export dialog details*) and `ui.state` windows carry `export`.

### Contract delta (T-090), accepted (autobuild, see docs/autobuild/DECISIONS.md "T-090 one engine", "T-090 feedback guard")
Additive. `device.list` devices carry `isBuiltIn`, `outputIsHeadphones` and `isDefaultInput` (08 delta T-090). In the app (attach mode), `ui.state` gains the following (12 *One live engine*, *Monitoring feedback guard*):
- `liveWindow` (top level): the id of the window that holds the live engine; null with `--engine offline` or without windows.
- Per window: `engine: {live, mode: realtime|offline} | null` and `feedbackWarning: {tracks[{id, name, monitoring, armed}], input{id, name}, output{id, name}, toast} | null`.
- The `audioPreferences` devices carry the three new fields.

### Contract delta (T-096), accepted (autobuild, see docs/autobuild/DECISIONS.md "T-096 control additions")
Additive. New methods and one new `render.offline` param; tools `daw_render_cancel`, `daw_engine_meters`, `daw_engine_preview_note` (CTL-021 naming). Two new error codes (CTL-003): -32005 `cancelled`, -32006 `notSupported`.
- **`render.offline {…, dither?}`** (DW-219, IO-035): TPDF dither for `int16`/`int24`, **default true** for them (as the docs already said); ignored for `float32`, which is never dithered. Seeded, so renders stay bit-identical (CTL-004). `dither: false` quantizes plainly (the `export_normalize` golden asks for that, so its reference is unchanged).
- **`render.cancel {id?}` → `{cancelled, id?}`** (DW-220): asks the engine to stop the `render.offline` that is waiting for its job (08 Contract delta (T-096) `cancelJob`). `id` is that request's JSON-RPC id (as in its `progress` notifications); without it, whichever render runs. It runs **outside the request queue** (CTL-031's one-at-a-time rule doesn't hold it back), so it can arrive while the render runs: from dawmcp (MCP tool calls run concurrently), from another socket connection (`dawctl --attach render.cancel` in another shell; dawmcp's attach mode opens its own short connection for it, since one connection's requests run in order), or in-process. `cancelled: false` (not an error) when no render runs or the id doesn't match. The cancelled `render.offline` then fails with -32005 `cancelled`; its progress stops below 1 (CTL-031 otherwise unchanged) and its partial file is deleted. Its RT violations still count in `engine.telemetry`.
- **`engine.meters {nodes?}` → `{meters: [{node, kind, peakDb: [..], rmsDb: [..], gainReductionDb?}]}`** (DW-174): read from the engine now (`EngineProtocol.meter`). `nodes` are model IDs; the default is every track, bus and the master, then every built-in compressor slot (track inserts and instruments, bus inserts, master inserts, in project order). `kind` is `track | bus | master` (post-fader strip meter, MIX-005: `peakDb`, `rmsDb` = 300 ms RMS, dBFS, -240 for silence; one value each, since the strip meters L and R together) or `compressor` (DSP-031: `peakDb`/`rmsDb` empty, `gainReductionDb` = the deepest reduction of the last block, ≤ 0 dB, makeup not included; 0 before it has processed audio). An entity without a meter is `invalidArgument`; an unknown ID `notFound`. After `render.offline`, the meters hold the render's last block; on a realtime engine they follow playback and previews.
- **`engine.previewNote {track, pitch, velocity? = 100, durationMs? = 500}` → `{track, pitch, velocity, durationMs}`** (DW-189): UI-021's audition through `EngineProtocol.previewNote`: the note-on now, its note-off `durationMs` later; the call returns at once. Realtime engines only (`project.new {engine: {mode: "realtime"}}`, fake device included): an offline engine answers -32006 `notSupported`. `track` must be a MIDI track with an instrument (`invalidArgument` otherwise, `notFound` if unknown); `pitch` 0…127, `velocity` 1…127, `durationMs` 1…60000 (`invalidParams`). To hear it, read `engine.meters` while it sounds.
- **App** (12 *Export dialog details*): while an export runs the dialog shows Cancel, `ui.perform` id **`export.cancel`** (disabled once pressed). It cancels the engine job; the dialog stays open, posts an info toast "Export cancelled", and sets no error.

### Contract delta (T-098), accepted (autobuild, see docs/autobuild/DECISIONS.md "T-098 control additions")
Additive: new methods and tools. Existing methods, params and results keep their meaning. Tools follow CTL-021's naming: `daw_plugins_scan`, `daw_plugins_list`, `daw_plugins_blocked`, `daw_plugins_retry`, `daw_plugins_unblock`, `daw_engine_param_display`. `list`, `blocked` and `paramDisplay` are read-only.
- **`plugins.*`** (DW-016, PLUG-001..004). The cache is 10's `plugins.json`; plugin code never loads in the calling process. A plugin is `ControlPlugin`: `{format: au|vst3, identifier, name, vendor, version, isInstrument, hasSidechain, numParams, status: ok|blocked, reason?, timedOut?}`. `identifier` is the scanner's (AU `type:subtype:manufacturer`, VST3 `path#classUID`; a blocked VST3 bundle the scanner couldn't report on: its path).
  - **`plugins.scan {timeoutSeconds?}`** → `{scanned, scannedCandidates?, unchanged, removed, plugins, blocked, timeoutSeconds, note?}`. It scans new or changed candidates and drops vanished ones (`PluginCatalog.refresh`). Blocked entries stay blocked. `timeoutSeconds` is each scan's limit, default 30 and at most 3600 (`invalidParams` outside (0, 3600]).
  - **`plugins.list`** → `{plugins, cachePath}`: the usable plugins.
  - **`plugins.blocked`** → `{blocked, cachePath}`: the blocked plugins, with reasons.
  - **`plugins.retry {id?, timeoutSeconds?}`** → `{retried, scan, stillBlocked}`. It forgets the blocked plugin `id` (all of them without it) and scans again (`retryBlocked`). The default limit is 120 s when a retried plugin had timed out (the plugin manager's "Retry (120 s)", DW-275), else 30 s.
  - **`plugins.unblock {id?}`** → `{unblocked}`. It forgets them without scanning (`resetBlocked`), so the next `plugins.scan` tries them again.
  - An `id` that isn't blocked is `invalidArgument`. A scanner that can't run is `internalError`, and nothing is cached.
  - *Headless* (`dawctl`, `dawmcp`, `CatalogPluginControl`):
    - Scanner: `PluginScanner` next to the binary (`scripts/dawmcp.sh` builds it), or `$DAWCTL_PLUGIN_SCANNER`.
    - Cache: `<checkout>/.build/plugins/plugins.json`, first copied from the user's cache so it lists what the app's scans found. Its own scans never write the user's file or another worktree's (CONV §9). `$DAWCTL_PLUGIN_CACHE` names another file.
    - Folders: `$DAWCTL_VST3_DIRS` (colon-separated) replaces PLUG-003's VST3 folders. `$DAWCTL_AU=0` leaves out audio units.
    - The cache is re-read on every call, so separate `dawctl` runs share it.
  - *Attach mode*: the app's plugin manager (UI-041). The app's UI provider implements `ControlPluginProvider` (`Dispatcher.Configuration.plugins` is the explicit hook), so the panel shows what a scan through the socket found. Differences from headless:
    - `scan` uses the app's own 30 s limit (a given `timeoutSeconds` is reported in `note`);
    - summaries have counts only (no `scannedCandidates`);
    - `plugins.unblock` is -32006 `notSupported` (the manager rescans what it forgets; use `plugins.retry`).
- **`engine.paramDisplay {node, param, value?}`** → `{node, param, value, display}` (DW-289): the facade's `paramDisplay` (08 "Contract delta (T-094)").
  - `node` is a device slot hosting an AU/VST3 plugin, as `engine.pluginInfo`'s `slot`; `param` is the index in its `params`.
  - `value` is VST3 normalized, AU in the param's range. Without it, the param's current `value` from `pluginInfoJSON` is used; then a slot without a loaded plugin, or an unknown param, is `invalidArgument`.
  - `display` is the plugin's own string without the unit, `""` when it has none (the host formats the number).
- **`dawctl` Ctrl-C** (DW-283): SIGINT while `render.offline` runs sends `render.cancel {id}` for it: in-process headless, or over a side connection with `--attach`/`--socket`. The render fails with -32005 `cancelled` and deletes its file, and dawctl exits 1 (a script stops there). SIGINT with no render running, a second one, or a render still running 10 s later exits 130.
- **dawmcp `tools/call` order** (DW-163): calls run strictly in arrival order. stdin passes through a tagger that numbers each `tools/call` in `params._meta["dev.emberstudio.dawmcp/seq"]` before the SDK, which runs each request in a task of its own, sees it. `daw_render_cancel` isn't numbered (it must reach the render it cancels). A numbered call the SDK never hands over (cancelled by `notifications/cancelled`, or dropped) releases its turn, at the latest 5 s after it came up. Execution is ordered; responses can still be written slightly out of order (a turn passes on when the handler returns, before the SDK writes its response), which JSON-RPC allows, since responses carry their ids.
- **Stale dawmcp** (DW-147, DW-151): while dawmcp's executable on disk is newer than its launch, every tool result (errors too) ends with an extra text item `stale: dawmcp binary rebuilt since launch; restart the MCP server …`. It doesn't restart itself (the session's project would be lost). The engine is linked into the binary, so its date covers engine changes. `scripts/dawmcp.sh` records its build check in `.build/debug/dawmcp.stamp` instead of touching the binary, so a build that changes nothing doesn't mark a running server stale. `scripts/dawmcp.sh --help` and 14's *Agent verification recipe* say so.
- **Also:** `midi.inject`'s summary (`dawctl methods`, the tool description) names `source?` (DW-285). `dawctl`'s fixture lookup is `ControlFixtures.defaultDirectories()` (DW-132). `GoldenEngine` and `EngineClient` share one `TelemetryPOD` conversion, `EngineClient.telemetry(from:)` (DW-240).

Affected: T-098 only. Tests: `ToolingFollowupTests` (DAWControlTests), `CallOrderTests` and `LauncherTests` (DawmcpTests), `EngineTelemetryConversionTests` (GoldenTests).
